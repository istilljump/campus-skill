## 6.1 高并发抢单：两级防线 + 原子化削峰

抢单是全系统竞争最激烈的接口。设计目标是：**正确性上"恰好一人成功"，性能上把无效竞争挡在数据库之前**。

**第一级：Redis Lua 原子脚本削峰。** 将"限流计数（INCR + EXPIRE）"与"订单占位（SET NX EX）"合并为一次 EVAL 往返：

```lua
local c = redis.call('INCR', KEYS[1])
if c == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
if c > tonumber(ARGV[2]) then return -1 end        -- 限流拒绝
if redis.call('SET', KEYS[2], ARGV[3], 'NX', 'EX', ARGV[4]) then return 1 else return 0 end
```

基线实现需要 INCR、EXPIRE、SETNX、DEL 共 4 次 Redis 往返；优化后失败请求只付 1 次往返成本，且拒绝动作发生在任何数据库访问之前。

**第二级：MySQL 条件更新兜底。** 无论 Redis 层结果如何，最终以

```sql
UPDATE orders SET runner_id = ?, status = 3
WHERE id = ? AND status = 2 AND pay_status = 1
```

的影响行数判定成败——数据库行锁保证并发条件下仅一人更新成功，即**正确性不依赖缓存层**，Redis 故障时系统退化为"全部打到条件更新"仍保持正确。

**第三项优化：接单权限本地缓存。** 权限校验（技能者认证状态 + 当日接单数）原为每次 2 次查库；改为本地缓存（允许 30s / 拒绝 5s）后，热点订单的瞬时请求绝大多数不再打库，显著缓解连接池争用。代价是封禁类风控变更最多延迟 30 秒生效，在抢单场景下可接受。

**A/B 验证**：为量化收益，同一构建通过 `--campus.grab.legacy` 参数保留基线实现路径，100 并发 × 8 轮对比：QPS +25.3%、平均时延 −19.0%、P95 −23.1%（详见第 5.6 节）。

## 6.2 担保交易的资金一致性与状态机

资金链路围绕"**结算时点 = 验收**"设计：支付即托管（用户余额扣出，技能者未到账），验收时按 `技能者实得 = 悬赏 − 类目费率` 结算，取消/超时/仲裁退款则原路退回。

关键机制有三：

1. **余额原子变更**：所有余额变动走条件更新 `UPDATE wallet_account SET balance = balance + ? WHERE id = ? AND status = 1 AND balance + ? >= 0`，影响行数为 0 即余额不足或冻结，天然防止透支与并发丢失更新；

2. **状态机约束**：订单 9 个状态的每次迁移都由带前置状态的条件更新完成（如验收 `WHERE status = 4`），配合返修次数上限（≤2 次）由数据库状态校验，杜绝"已完成的订单再发货"这类非法迁移；

3. **对账不变量**：任意并发操作序列后，`余额 = 初始 + Σ成功收入 − Σ成功支出` 且与钱包流水一一对应。该不变量被抽象为并发集成测试（第 5.5 节），是资金安全的回归保障。

## 6.3 并发懒开户：一次真实的竞态缺陷修复

钱包采用懒开户（首次资金操作时创建账户）。原实现为"查询 → 不存在 → 插入"的检查-插入模式，并发对账测试（20 线程首充）暴露了两层问题：直接竞争触发唯一键冲突（7/20 失败）；朴素的"冲突后重查"在 REPEATABLE READ 下读到旧快照仍为空，而"对不存在行做锁定读"又会与并发插入形成间隙锁互斥导致死锁。

最终方案：**Redis 分布式锁串行化同一用户的开户插入 + 等待方对已存在行做行锁读**。持锁者在自身事务内插入（行已存在，等待方的锁定读阻塞在其行锁上直至事务提交），等待方全程不持有与插入冲突的间隙锁。修复后 20/20 成功，余额对账精确。该过程说明：分布式场景下"检查-插入"类逻辑必须显式串行化，且锁的粒度与事务边界需要一起设计（详见第 5.5 节缺陷案例）。

## 6.4 个性化推荐引擎：三路混合打分与可解释性

冷启动是小平台推荐系统的核心矛盾。本项目采用 **ItemCF 协同过滤 + 内容特征 + 质量因子** 三路加权（0.45/0.30/0.25）：

- **ItemCF**：基于全体用户近 90 天加权行为矩阵（浏览 1.0 / 预约 3.0 / 成交 5.0）计算服务间余弦相似度，行为权重让"成交"比"浏览"更能表达偏好；
- **内容特征**：类目偏好（用户历史行为类目占比）+ 标签 Jaccard 相似度 + 价格贴近度，解决行为稀疏时相似度不足的问题；
- **质量因子**：销量、均分、技能者信用与作品定级，保证结果基础可信度，同时**独立承担冷启动兜底**——无行为用户直接按质量分排序（"热门精选"）。

工程上有三个设计点：行为埋点为旁路逻辑（失败仅记日志，不影响交易主流程）；浏览行为 30 分钟窗口去重防刷；已成交与本人挂牌服务强制排除、近期浏览过服务降权 0.6，避免重复曝光。每个推荐项附带人类可读的 `recommendReason`（如"与你互动过的服务相似"），实现**可解释推荐**。

效果经对比实验验证：模拟偏好驱动用户场景下，推荐位兴趣类目命中率 36.7%（对照组 0%）、预约转化率 14.7%（对照组 0%），详见第 7 章。

## 6.5 安全性设计

- **口令存储**：BCrypt 慢哈希（`PasswordUtil` 统一封装）。存量 MD5(salt+明文) 口令在登录成功时自动重哈希升级（渐进迁移），无需重置用户密码；
- **三端身份隔离**：用户端 `/user/**`、技能者端 `/skiller/**`、管理端 `/admin/**` 各自独立 JWT 拦截器与签名密钥，token 不可跨端使用；
- **登录体验**：账号不存在与密码错误统一提示，防止账号枚举探测；
- **降级入口管控**：体验码登录（任意码即可登录）为联调/演示专用，`campus.guest-login.enabled` 配置开关，生产环境关闭；
- **风控约束**：抢单接口限流（10 秒 5 次）、每日接单上限、提现密码 + 冻结 + 审核、仲裁判责自动扣信用分。

## 6.6 部署与工程化

Maven 多模块（common/pojo/server）分层清晰；前端构建产物经 `tools/build-frontends.mjs` 同步进 SpringBoot 静态目录随 jar 一起发布，避免"源码改了、包里还是旧页面"；SQL 演进以带版本号的升级脚本管理（v2~v10，均为幂等或守卫式），`tools/reset-demo.bat` 一键重建演示环境。测试资产（单元/并发/E2E/压测）与文档（接口文档-三端、数据库设计、本文各章节）均纳入仓库版本管理。
